# 4～5 分钟演示脚本

## 演示前准备

```powershell
# 完全离线、最快的稳定演示
$env:EMBEDDING_BACKEND="hashing"
streamlit run app.py
```

浏览器打开 `http://localhost:8501` 后，先进入“岗位库”，点击“一键加载 30 条官方 JD”。不要运行合成岗位导入脚本。

候选人侧继续使用 `data/evaluation/demo_resume.md`。这是一份合成简历；不要在公开演示中上传真实未脱敏简历。演示数据口径是：**真实官方公开 JD + 合成候选人 + 双模型独立盲标与裁决形成的模型辅助评测基准**，不是基于真人专家标注的金标准。

## 时间线

1. **0:00～0:30 痛点与定位**：岗位 JD 表述不统一，候选人难以比较，也容易为了关键词误改简历。本项目把硬规则、语义和证据拆开，让推荐结果能够解释和审计。
2. **0:30～1:05 官方岗位库**：点击“一键加载 30 条官方 JD”，展示状态看板中的 **30 条岗位、27 条在招、2 条过期、1 条待确认**。筛选在招岗位，并打开一条“官方来源”链接，说明数据来自仓库内已核验快照，演示过程不联网抓取。
3. **1:05～1:40 简历解析**：上传合成文件 `data/evaluation/demo_resume.md`，展示技能、教育和项目原文，并强调结构化结果可人工修正。明确这是合成候选人，不是真实求职者数据。
4. **1:40～2:30 岗位推荐**：运行 **Top-5**，展示每张卡片的状态、核验日期和岗位来源。打开第一名，解释六项分数、技能命中、缺口与简历证据。
5. **2:30～3:10 简历优化**：展示一条由简历原文支撑的“可直接修改”建议，同时对比“完成相关工作后才能加入”，说明系统不会把待学习能力写成既有经历。
6. **3:10～3:40 模拟面试**：打开一题岗位定制面试题，展示考察点、回答结构、追问与关联证据。
7. **3:40～4:30 实验看板**：先指出 UI 披露的实际 embedding 后端，再展示真实 JD 上的方法对比。BGE-M3 CPU 实测耗时 64.7194 秒、1024 维且无 fallback；纯语义 Recall@5 从 0.1373 升至 0.4314、nDCG@5 从 0.5436 升至 0.6451，但 Recall@10 从 0.6275 降至 0.5294，full nDCG@5 也从 0.6962 微降至 0.6940，因此不要宣称全面提升。同时展示 47.78% 精确一致率、二次加权 κ 0.3751、47 条分歧与 8 条严重分歧，并说明候选人是合成的，标签是**模型辅助评测基准，不是真人金标准**。
8. **4:30～5:00 工程与边界**：说明 SQLite、本地离线、官方数据快照、完整测试、Docker、删除分析记录和不存完整简历；系统不登录招聘网站，也不自动投递。

## 简历项目描述

**秋招雷达 AI｜岗位匹配与简历优化 Agent**：构建支持 PDF/DOCX/TXT/Markdown 的简历解析与上海 AI 校招岗位匹配系统，设计硬规则、项目技能与离线语义相似度的六维融合评分，输出可追溯的技能缺口、简历建议及岗位面试题；实现 SQLite 去重存储、Markdown 报告、Streamlit/Docker 部署，并用 F1、Recall@K、MRR、nDCG 和五组消融实验验证完整管线。

## 面试展开点

- 为什么地点和学历是硬约束，而不是相似度的一部分？
- 如何避免技能别名漏召回，以及别名表的维护成本？
- 为什么合成集 nDCG 很高但 Recall@5 不高？
- 为什么 BGE-M3 改善了纯语义 Top-5，却没有改善 full nDCG@5 和 semantic Recall@10？
- 证据约束如何阻止系统把“建议学习”写成“已经掌握”？
- 从单机 Demo 到生产系统还需要哪些权限、监控、数据治理和评测机制？
